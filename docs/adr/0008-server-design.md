# 0008. 서버는 구성요소 대응을 전역으로 한 번만 계산하고, 프로젝트별 발견은 멱등하게 맞춘다

- 상태: 채택 (2026-11-19)

## 맥락

CLI는 빌드 한 번을 그 시점에 점검한다. 경매톡에서는 점검 8일 뒤 공개된 guava 권고를 CI의 매일 실행이 잡았다(사례 8절). 하지만 그 방식은 프로젝트마다 CI가 매일 빌드를 돌려야 하고, "어느 프로젝트가 영향을 받는가"를 한 번에 볼 수 없다.

## 결정

1. **저장 단위는 SBOM 스냅샷이다.** 빌드는 CI가 하고, 서버는 결과물(CycloneDX)만 받는다. 빌드 도구(Gradle·Maven)와 무관해진다.
2. **"버전 ↔ 권고" 대응은 전역 테이블 하나로 둔다.** spring-webmvc 6.2.19에 어떤 권고가 걸리는지는 어느 프로젝트가 쓰든 같은 사실이다. 프로젝트가 100개여도 같은 버전은 OSV에 한 번만 묻는다.
3. **발견은 (프로젝트, 구성요소, 권고)당 하나만 둔다.** 상태만 OPEN ↔ RESOLVED로 바꾼다. DB 유일 제약으로 강제한다. 같은 SBOM 재업로드, 재검사 중복 실행, 실패 후 재실행이 모두 같은 결과를 낸다(멱등).
4. **외부 API 호출은 DB 트랜잭션 밖에서 한다.**
   - 업로드: 스냅샷 저장 → (트랜잭션 없이) OSV 조회 → 대응 저장 → 상태 맞추기. 세 개의 짧은 트랜잭션으로 나눈다.
   - 재검사(Spring Batch): 청크 트랜잭션을 리소스 없는 트랜잭션 매니저로 두고, 저장만 JPA 트랜잭션으로 한다. 저장이 멱등이라 청크 재실행이 안전하다.
   - OSV가 느려져도 DB 커넥션 풀이 먼저 고갈되지 않게 하려는 것이다.
5. **업로드 시 최근 24시간 안에 조회한 구성요소는 다시 조회하지 않는다.** 매일 재검사가 최신성을 보장하므로, 업로드는 새 구성요소만 조회하면 된다.
6. **알림 정보는 트랜잭션 안에서 만든다.** 새 발견의 구성요소·권고는 지연 로딩 프록시라, 트랜잭션이 끝난 뒤 읽으면 실패한다.

## 근거

- 실제 OSV로 세 프로젝트(구성요소 355개, 중복 제외 342개)를 올렸을 때, 두 번째·세 번째 프로젝트는 각각 1개·12개를 이미 조회된 것으로 재사용했다. 같은 SBOM 재업로드는 OSV 조회 없이 0.04초에 끝났다(첫 업로드 1.95초).
- 서버의 발견 수가 CLI `analyze` 결과와 세 프로젝트 모두 일치했다. 같은 분석 코드(OSV 클라이언트, 좌표)를 공유하기 때문이다.

## 한계와 다음 단계

- 예외(ADR 0003), NVD 보완(ADR 0006), 라이선스(ADR 0004)를 서버로 옮기지 않았다.
- 서버를 여러 대 띄우면 스케줄 실행이 중복된다. 분산 락(ShedLock 등)이 필요하다. 저장이 멱등이라 중복 실행이 결과를 망가뜨리지는 않지만, OSV 호출이 늘어난다.
- 재검사는 모든 사용 중 구성요소를 매일 다시 조회한다. 규모가 커지면 OSV의 변경분 피드(modified 기준)를 받아 바뀐 권고만 반영하는 방식이 필요하다.
