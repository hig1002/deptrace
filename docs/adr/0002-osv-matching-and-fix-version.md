# 0002. 취약 여부는 OSV에 맡기고, 수정 버전은 직접 계산한다

- 상태: 채택 (2026-10-19)

## 맥락

Maven 생태계의 취약점 매칭 방식은 크게 둘이다.

- **CPE 기반 (NVD):** 제품 단위로 묶여 있어, 한 제품의 여러 모듈(예: netty-*)에 같은 CVE가 매칭되기 쉽다.
- **좌표 기반 (OSV, GHSA):** `group:artifact`와 버전 범위로 매칭한다.

## 결정

1. 좌표(purl)로 OSV `/v1/querybatch`를 호출해 영향 여부를 판정한다. 판정 로직은 재구현하지 않는다.
2. 수정 버전은 OSV 상세 데이터의 영향 범위 이벤트로 직접 계산한다.
3. 계산한 수정 버전은 Maven Central `maven-metadata.xml`로 실제 배포 여부를 확인한다.

## 근거

- **영향 여부 판정을 직접 하지 않는 이유:** OSV-Scanner와 같은 데이터·규칙을 쓰는 영역이다. 다시 만들 가치보다 오차 위험이 크다. 실제로 경매톡 배포 클래스패스 기준 163쌍이 OSV-Scanner와 모두 일치하는 것으로 확인했다.
- **수정 버전은 직접 계산해야 했다.** 권고는 릴리스 라인별로 범위를 따로 둔다. 경매톡에서 본 두 경우가 단순 계산으로는 틀린 답을 낸다.
  - **Spring Framework 6.1.x:** 범위가 `introduced 6.1.0 / last_affected 6.1.21`로 끝나고, 공개 수정 버전은 6.2.19에만 있다. "가장 가까운 fixed"를 고르면 패치 업그레이드로 해결되는 것처럼 보이지만, 실제로는 라인을 옮겨야 한다.
  - **software.amazon.ion:ion-java:** 이 좌표에는 수정 버전이 없고, 같은 권고가 `com.amazon.ion:ion-java` 1.10.5에만 수정 버전을 둔다. 좌표가 이동한 경우다.
- **배포 확인이 필요했다:** Tomcat 권고의 수정 버전 10.1.58은 Maven Central에 배포된 적이 없다(10.1.57 다음이 10.1.59). 그대로 권고하면 빌드가 실패한다.

## 결과

- 결과는 권고마다 `fixedInLine`(같은 라인), `nextSafe`(어떤 영향 범위에도 걸리지 않는 가장 낮은 fixed), `alternatives`(다른 좌표의 수정 버전)로 나뉜다.
- 구성요소 단위 수정 버전은 `nextSafe`의 최댓값이고, 배포 확인을 거친 값은 `publishedFixVersion`이다.
- CVE↔GHSA 별칭은 CVE를 대표 ID로 삼아 묶는다. 같은 권고가 여러 모듈(spring-webmvc, spring-webflux)에 걸려도 고유 취약점은 한 번만 센다.
