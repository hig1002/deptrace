# 0006. OSV 공백은 명시적 제품 대응표와 NVD 설정 평가로 보완하고, 제품 단위로 보고한다

- 상태: 채택 (2026-11-18)

## 맥락

경매톡을 OWASP Dependency-Check와 교차 검증하니, DepTrace(OSV)가 놓친 CVE가 26건이었다(사례 11절). 모두 GitHub 권고가 **미검토** 상태였다. OSV의 Maven 데이터는 GitHub이 검토해 패키지에 연결한 권고에서 오므로, 검토가 끝나기 전에는 보이지 않는다. Spring 권고는 공개 3개월이 지나도 미검토였다.

반대로 Dependency-Check는 같은 비교에서 오탐 74쌍을 냈다. 원인은 둘이었다.
- jar 이름으로 제품을 추측하다 생태계를 틀림 (Go·JavaScript용 OpenTelemetry 권고가 Java jar에, querydsl이 `homepage_project:homepage`로)
- 제품 단위 권고를 jar마다 붙임 (log4j-core 권고가 log4j-api에, webmvc 권고가 spring-core 등 13개에)

## 결정

1. **보완이지 대체가 아니다.** OSV가 보고한 CVE는 빼고, OSV가 아직 모르는 것만 찾는다.
2. **명시적 제품 대응표.** Maven 모듈과 NVD 제품(CPE vendor:product)의 연결을 [표](../../src/main/resources/deptrace/nvd/products.yml)로 적는다. 표에 없는 모듈은 보지 않는다. 버전 체계가 다른 하위 모듈(netty-tcnative)과, 권고 대부분이 해당하지 않는 모듈(log4j-api)은 표에서 뺀다.
3. **NVD 설정을 논리식으로 평가한다.**
   - 설정·노드의 AND/OR를 따른다. 다른 제품 조건은 클래스패스 버전으로 확인한다.
   - OS·JRE처럼 클래스패스로 알 수 없는 조건은 만족하지 않는 것으로 본다.
   - target_sw가 Java 계열이 아니면 제외한다.
   - 버전 `-`는 "해당 없음"이라 제외한다.
4. **검토된 판단을 존중한다.** GitHub이 검토해 다른 Maven 패키지에 연결한 CVE는 뺀다. 검토 결과가 "그 모듈이 아니다"라고 말하고 있기 때문이다.
5. **제품당 한 번 보고한다.** 어느 jar의 문제인지는 NVD가 알려주지 않는다. jar마다 세면 같은 권고가 15번 나온다.
6. **다음 안전 버전은 배포 여부까지 확인한다.** NVD의 수정 버전(Spring 6.2.20 등)이 상용 지원판에만 있는 경우가 있어, Maven Central에 실제로 있는 버전 중 같은 CVE의 어떤 범위에도 들지 않는 가장 낮은 것을 고른다.

## 근거: 경매톡 측정

| 지표 | 결과 |
|---|---|
| 기준(11절에서 확인한 OSV 누락 26건) 재현율 | 26/26 |
| 기준 밖 추가 보고 | 0 |
| Dependency-Check 오탐 CVE 13건 재등장 | 0 |

첫 구현에서는 추가 보고가 2건 있었다. RHEL Tomcat 패키지 권고(버전 `-`, OS AND 조건)였고, 위 3번 규칙을 추가해 고쳤다. 같은 수정으로 CVE-2018-1258("Spring Security AND Spring Framework 5.0.5")이 더 이상 범위에 들지 않게 됐다. 이전에는 GitHub 검토 데이터 덕분에 우연히 걸러졌을 뿐, 판정 자체는 틀렸었다.

## 한계

- 대응표에 있는 14개 제품만 본다. 표를 넓히는 일은 사람이 NVD에서 CPE 이름을 확인해야 한다.
- 어느 jar·기능의 문제인지는 사람이 권고 내용을 보고 판단한다.
- 기준 데이터가 경매톡 한 프로젝트라, 다른 프로젝트에서도 같은 정확도를 낸다고 말할 수는 없다.
- NVD 분석이 늦거나 틀리면(범위 누락) 그대로 따라간다.
