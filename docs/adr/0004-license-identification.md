# 0004. 라이선스는 POM 선언을 SPDX로 정규화하고, 모르는 것은 추측하지 않는다

- 상태: 채택 (2026-11-18)

## 맥락

취약점은 OSV라는 정리된 데이터가 있지만, 라이선스는 각 프로젝트가 POM에 자유 형식으로 적는다. 경매톡 배포 클래스패스 292개에서 Apache-2.0 하나만 7가지 표기로 나왔다("Apache 2", "Apache License, version 2.0", "The Apache Software License, Version 2.0" 등). 또 292개 중 105개는 자기 POM에 선언이 없고 부모 POM에서 상속받는다.

## 결정

1. **출처:** Maven Central의 POM `<licenses>`. 없으면 `<parent>`를 최대 10단계까지 따라간다. POM은 배포 후 바뀌지 않으므로 만료 없이 캐시한다.
2. **식별 순서:** SPDX 식별자 그대로 → 정규화한 이름 → URL. URL은 가장 긴(구체적인) 패턴이 맞는 것을 고른다.
3. **모르는 것:** 매핑 표에 없으면 추측하지 않고 `NOASSERTION`(UNKNOWN)으로 남긴다. "Apache License"처럼 버전이 없는 표기도 식별하지 않는다. 조항 수가 없는 "BSD License"는 분류(허용형)는 확실하므로 `LicenseRef-BSD`로 둔다.
4. **다중 라이선스:** OR(그중 하나를 선택)로 본다. Maven 모델 레퍼런스(maven-model의 `licenses` 설명)가 "여러 라이선스가 나열되면 사용자가 그중 하나를 고를 수 있다"고 정의한다. 판정에 쓴 선택지를 리포트에 남긴다.
5. **분류:** 의무 강도 기준 5단계(허용형, 약한·강한·네트워크 카피레프트, 미확인). 무엇을 막을지는 분류와 분리해 정책 파일에서 정한다.

## 근거

- **이름을 URL보다 먼저 본다.** 실제 데이터에서 URL만 보면 틀리는 경우가 나왔다.
  - hibernate-core: 이름은 "GNU Library General Public License v2.1 **or later**"인데 URL은 LGPL 2.1 원문이라, URL만 보면 `LGPL-2.1-only`가 된다.
  - jakarta.*: "GPL2 w/ CPE"(Classpath 예외)를 URL만 보면 예외 없는 GPL이 되어 강한 카피레프트로 잘못 분류된다.
- **더 긴 URL을 우선한다.** `opensource.org/licenses/mit`는 `opensource.org/licenses/mit-0`의 앞부분이라, 부분 일치만 하면 MIT-0(고지 의무 없음)이 MIT로 묶였다. 실제로 첫 실행에서 이 오류가 나왔다.
- **추측하지 않는다.** 라이선스 판정은 오탐보다 미탐이 비싸다. 모르는 것을 허용형으로 추측하면 금지 라이선스가 통과할 수 있다. 미확인은 검토 목록에 올려 사람이 본다.
- **분류와 정책을 분리한다.** 같은 GPL이라도 서버에서만 실행하는 서비스와 설치형으로 배포하는 제품은 의무가 다르다. 분류는 사실, 금지 여부는 조직의 판단이다.

## 경매톡에서 나온 판단 사례

MySQL Connector/J 9.7.0은 "GPL v2 with Universal FOSS Exception"이다. 이 예외는 결합한 프로그램이 오픈소스 라이선스일 때만 GPL 전파를 면제하므로, 비공개 소스 서비스에는 적용되지 않는다. Classpath 예외(약한 카피레프트)와 달리 강한 카피레프트로 분류했고, 기본 정책에서 게이트가 실패했다.

## 한계

- POM 선언만 본다. JAR 안의 LICENSE 파일이나 소스 헤더와 다른 경우, 재패키징된 코드의 원래 라이선스는 잡지 못한다.
- 다중 라이선스를 AND 의미로 나열한 프로젝트는 OR 가정이 틀린다.
- 매핑 표는 경매톡과 흔한 표기를 기준으로 만들었다. 새 표기는 미확인으로 나오고, 확인 후 표에 추가한다.
