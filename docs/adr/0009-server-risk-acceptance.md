# 0009. 서버의 예외는 발견 상태(ACCEPTED)로 표현하고, 만료되면 다시 열어 알린다

- 상태: 채택 (2026-11-19)
- 관련: ADR 0003(CLI 예외 규칙), ADR 0008(서버 설계)

## 맥락

CLI는 예외를 `deptrace-exceptions.yml`로 관리한다. 게이트를 돌릴 때마다 파일을 읽고, 만료되면 게이트가 실패한다. 서버에서는 발견이 시간에 따라 상태를 가지므로, 예외도 "언제 누가 왜 수용했고, 언제 끝났는지"를 기록해야 한다.

## 결정

1. **발견 상태에 ACCEPTED를 추가한다.** 예외로 덮인 발견은 지우지 않고 수용 상태로 둔다. 열린 발견 수와 영향 조회(조치가 필요한 것)에서는 빠지고, 어떤 예외가 덮는지(사유·만료일)는 발견에 남는다.
2. **규칙은 CLI와 같다.**
   - 권고는 GHSA ID 또는 CVE 별칭으로 지정한다.
   - 모듈(group:artifact)은 선택이다.
   - 사유와 만료일은 필수이고, 만료일 당일까지 유효하다.
3. **정책을 서버가 강제한다.**
   - 사유는 10자 이상이어야 한다. 확인 방법을 적게 하려는 것이다.
   - 만료일은 오늘 이후, 최대 180일까지만 받는다(설정 가능). 기간을 길게 잡으면 다시 볼 시점이 사라진다.
4. **상태 전이는 하나의 조정(reconcile) 함수에 모은다.** 예외를 만들거나 철회하면 그 프로젝트를 바로 조정한다. 만료는 매일 재검사의 조정이 날짜를 보고 처리한다. 별도의 "만료 처리 배치"를 두지 않는다. 판단 로직이 한 곳에 있어야 상태가 어긋나지 않는다.
5. **알림은 조치가 필요한 순간에만 보낸다.**
   - 새로 열림, 다시 나타남, 예외 종료(만료·철회)일 때 보낸다.
   - 예외가 미리 있어서 처음부터 수용된 발견은 알리지 않는다.
6. **철회는 삭제가 아니다.** `revoked_at`을 남겨, 누가 언제 무엇을 수용했다가 거뒀는지 감사할 수 있게 한다.

## 검증 (통합 테스트, 시각을 움직일 수 있는 시계 사용)

| 시나리오 | 결과 |
|---|---|
| CVE 번호로 예외 등록 | 발견 ACCEPTED, 열린 목록·영향 조회에서 빠짐 |
| 만료일 당일 재검사 | 여전히 ACCEPTED |
| 만료일 다음 날 재검사 | OPEN으로 돌아가고 "예외 종료" 알림 |
| 철회 | 바로 OPEN, 기록은 REVOKED로 남음. 토큰 없는 철회는 401 |
| 예외를 먼저 등록하고 취약 버전 업로드 | 처음부터 ACCEPTED, 알림 없음 |
| 다른 모듈을 지정한 예외 | 적용 안 됨 |
| 사유 10자 미만 / 지난 만료일 / 181일 | 400 (180일은 허용) |

## 개발 중 발견한 결함

재검사 잡의 식별 파라미터로 요청 시각(밀리초)만 쓰고 있었다. 고정 시계로 테스트하자 두 번째 재검사가 "이미 완료된 잡 인스턴스"로 거부됐다(500). 실제 시계에서도 같은 밀리초에 두 요청이 오면 생기는 문제라, 실행마다 고유한 runId를 식별 파라미터로 바꿨다.

## 한계

- 수용 승인 절차(요청자와 승인자 분리)는 없다. `requestedBy`는 기록만 한다.
- CLI의 `deptrace-exceptions.yml`을 서버로 가져오는 기능은 아직 없다. 두 곳에서 예외를 관리하면 어긋날 수 있다.
